BACKDRAFT原理
量 · 记 · 读 · 应用不用改一行代码

原理只有一句话。

一笔交易在结束之前，合约看得见自己还剩多少 gas。所以真实用量，在链上量得出来。

量

执行你的调用，前后各看一次还剩多少 gas。两次的差，就是你真正用掉的。Monad 的回执不会告诉你这个数，只有在链上才量得到。

记

用这笔交易里本来要作废的剩余 gas，把这个数按“合约 + 函数”记到链上。只写自己的一格存储，不碰任何人的状态。

读

之后任何钱包、Agent、合约读一次链，就拿到建议的上限：实测最大用量加 7.5% 余量。下一笔照着设，不再多付。

怎么接

你要设上限 —— 读一次链

你得到：这个合约的这个函数，链上实测用量加 7.5% 余量。官方文档点名要重查 gas 设置的跨链执行、4337、keeper、relayer，现在有地方查了。

// 这个函数实际用多少 gas？问链。
uint256 gasLimit =
    backdraft.suggestTxGasLimit(target, data);

你的应用想出一份力 —— 加一个词

你得到：用户的每一笔交易经过时顺手量一次、记一次。调用者不变，出错不影响你的函数。

contract MyApp is BackdraftHook {
    function swap(...) external recycle {
        // ……你自己的逻辑……
    }
}

你是 Agent —— 装上 MCP 实测

你得到：没有钱包替你设上限。发交易前先读一次流量计。

接下来三步
  • 草案已写提成 MRC

    登记表的接口已整理成 MRC 草案，在仓库里。

  • 规划进钱包和 SDK

    发交易前读一次流量计，一行代码。

  • 规划补全历史

    等官方通过 RPC 公开真实用量后，把历史数据批量补进来。

估算按官方研究的结论，全网多付的 gas 能从三成降到一成多；同样的区块能多装约四分之一的交易。算法：多付的占比从 32.5% 降到约 15%，执行的占比从 67.5% 升到约 85%，85 ÷ 67.5 ≈ 1.26（Category Labs 数据 ↗）。

今天的边界：只有经过它的交易才会被计量；只记最大值，输入变化大的函数还不够准，使用前要先估算一次；通过包装入口测量时调用者会变；合约未经审计，只在测试网运行。
